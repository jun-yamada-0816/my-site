# 星の海

1995年頃の個人ホームページをイメージした、静的HTMLとSupabaseのサイトです。
トップページは `index.html`、共通のレトロな見た目は `retro.css`、海のドット絵は `assets/starlit-sea.svg` にあります。

公開URLは https://hoshinoumi.org/ です。

## セキュリティの点検（2026-10-03）

`~/.claude/CLAUDE.md` の開発ルールと照らし合わせて見直しました。**下の「管理者だけに絞る」は、Supabase側の操作が済むまで効きません。**

### 管理者だけに絞る（要対応）

点検の時点で、Supabaseの**新規登録（Sign up）が開いていました**（`/auth/v1/settings` の `disable_signup: false`）。サイトの権限は「ログインしている人＝管理者」という前提（`auth.role() = 'authenticated'`）なので、誰かがメールアドレスでアカウントを作ると、日記・プロフィールの書き換えや削除、掲示板の削除、音楽のアップロード、YouTube分析のデータと **APIキー（`sv_config`）の読み取り**、ITニュースの収集元の追加までできる状態でした。掲示板の編集（`/api/bulletin`）だけは管理者のUIDで確かめているので対象外です。

1. Supabase → **Authentication → Sign In / Providers** で **Allow new users to sign up をオフ**にします。どのページにも登録画面はないので、オフにして困ることはありません。
2. `admin-only.sql` の `YOUR_ADMIN_USER_ID_HERE` を自分の User UID（Vercelの `BBS_ADMIN_USER_ID` と同じ値）に置き換えて、SQL Editorで全体を実行します。既存の権限はそのままに、「管理者の一覧（`site_admins`）に入っていないログインは何もできない」制限を重ねます。訪問者の読み取りや訪問の記録には影響しません。訪問の記録（`sv_site_visits`）には文字数の上限も付けます。
3. 最後に出るアカウント一覧で、`is_site_admin` が false のアカウントがないか確かめます。覚えのないアカウントがあれば削除し、**YouTubeのAPIキーを作り直してください**（読まれた可能性があるため）。日記・音楽に覚えのない変更がないかも見てください。

`docker` があれば、使い捨てのDBで `admin-only.sql` を確かめられます（本番には接続しません）。管理者・ほかのログイン・訪問者それぞれについて、読み書きできること／できないことを確認します。

```sh
docker run --rm --network none --tmpfs /var/lib/postgresql/data \
  --mount "type=bind,source=$PWD,target=/work,readonly" \
  -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16 sh /work/tests/run-admin-only-db.sh
```

残っていること：`sync_youtube()`・`refresh_it_news()`・`restore_metrics_from_log()` などのRPCは `security definer` で、ログインしていれば管理者でなくても呼べます。管理者が設定した取り込みを動かすだけで、データを読み出したり収集元を足したりはできませんが、新規登録をオフにしておくことが前提です。

### カフェ一覧は管理者だけに

`niigata-cafes-list.html` は以前、190件の店名・住所をページの中に書いていたため、管理者メニューから隠していても URL を知っていれば誰でも読めました。2026-10-03 から、一覧は Supabase の `admin_cafes` 表に置き、**管理者がログインしているときだけ**読み込みます（`admin-only.sql` の `is_site_admin()` を使います）。ページ自体は公開のままで、中に一覧はありません。ログインはトップページと共通なので、管理者メニューの「カフェ」から開けばそのまま表示されます。

- 表を作るには、`admin-only.sql` のあとに **`admin-cafes.sql`** を SQL Editor で実行します。実行するまでは、ページに「admin-cafes.sql を実行してください」と出ます。何度実行しても重複しません。
- 店を足したり直したりするときは、`admin-cafes.sql` の一覧を直して実行し直します（ページからは書き換えられません）。地図のリンクは店名と住所からページ側で作ります。
- 確認：`node tests/cafes.cjs`（ページ。Supabase は模擬）と、上の docker のコマンド（表の権限）。

### そのほかに直したこと

- **音楽の再生ボタン**：曲のURLを `onclick` の文字列に埋め込んでいたため、`'` を含むURLが登録されるとスクリプトとして動く状態でした。URLは読み込んだ一覧から引き、`https:` 以外は再生しないようにしました。

- **YouTube分析**：動画IDを画像・リンクのURLに入れる前に、YouTubeのIDに使われる文字だけかを確かめるようにしました。
- 訪問の記録で送る値を、DB側の上限と同じ長さに切ってから送るようにしました。

## 独自ドメインへの切り替え（hoshinoumi.org）

正規URLは **https://hoshinoumi.org/**（wwwなし）です。サイト内の共有・計測リンク、canonical・OGP、共有画像、掲示板通知、ニュース取得のUser-AgentをこのURLに統一しています。Supabaseの接続先・テーブル・保存キーは変更しません。

GitHubへのプッシュだけでは、DNS・Vercel・Supabaseの設定や既存のDB関数は更新されません。次の順で設定してください。

1. **旧ドメインから転送する前に**、入力に使ったブラウザーで https://hoshinoumi.vercel.app/shorts.html を開き、「分析の土台」と各動画・各計測日の未保存の数字を保存してください。ブラウザー内の控えとログイン状態はドメインごとに別です。新ドメインではログインし直し、クラウドの保存内容を読み込みます。確認が終わるまで旧ドメインを利用可能にしてください。
2. Vercelの既存のmy-siteプロジェクトで **Settings → Domains → Add Domain** から `hoshinoumi.org` を追加し、Productionに接続します。`www.hoshinoumi.org` も使う場合は追加します。
3. ドメインを取得したサービスのDNS設定で、**Vercelが表示するレコードの種類・名前・値**を登録します。既存のメール用MX・TXTなどは残してください。VercelでDNS検証とHTTPS証明書の発行完了を確認します。
4. Supabaseの **Authentication → URL Configuration** の **Site URL** を `https://hoshinoumi.org` に変更し、**Redirect URLs** に確認メール・パスワード再設定などで使う新URLの戻り先を登録します。同じSupabaseプロジェクトを使い、DBの作り直しやデータ削除は不要です。
5. 新URLでトップページ、日記の共有リンク、`/shorts.html`、`/it-news.html`、`/niigata-cafes-list.html`、`/assets/og-image.png` を確認します。管理者としてログインし、保存済みデータ、共有URL、UTMパラメーター付き計測リンクも確認してください。
6. 保存内容と新ドメインの動作を確認してから、Vercelで旧 `hoshinoumi.vercel.app` と任意の `www.hoshinoumi.org` を、正規ドメインへの恒久リダイレクトに設定します。旧ドメインは削除せず、パス・日記のクエリー・UTM・`#bulletin` が引き継がれることを確認してください。未保存データの回収を妨げないよう、リポジトリーには即時転送を追加していません。
7. YouTubeのプロフィールや投稿済み動画の説明文など、手動で掲載したURLも変更してください。動画識別子とUTMパラメーターは維持します。

掲示板通知SQLを導入済みの場合は、`bbs-moderation.sql` の `create or replace function public.notify_new_bulletin_message()` から対応する `$$;` までをSupabaseのSQL Editorで再実行してください。ニュース取得SQLを導入済みの場合も、`it-news.sql` の `create or replace function it_news_fetch_source(p_id uuid)` から対応する `$fn$;` までを再実行してください。既存の通知先・認証情報・トリガー設定は変更せず、関数内のURLを更新します。

訪問済み判定などのブラウザー内キャッシュもドメインごとに別なので、切り替え時に一度追加で訪問が数えられる場合があります。DBに保存済みの累積値はリセットしません。

参考: [Vercelのドメイン追加](https://vercel.com/docs/domains/working-with-domains/add-a-domain)、[ドメインのリダイレクト](https://vercel.com/docs/domains/working-with-domains/deploying-and-redirecting)、[SupabaseのURL設定](https://supabase.com/docs/guides/auth/redirect-urls)。

### 分析データの保存とプロンプト

「分析の土台」は入力中に従来と同じ `sv-strategy-v1` に控えを残し、「保存する」で管理者専用の `sv_config` の `shorts_strategy_v1` にも保存します。以前の端末内データは消しません。改修を反映したら、入力したときと同じブラウザー・同じURLで開き、内容を確認して一度保存してください。以後、同じSupabaseにログインする別の端末でも読み込めます。クラウドと異なる未保存の入力は端末側を残し、競合を知らせます。端末内の控えを書けない場合も表示します。

`sv_config` には既存の管理者向けRLSを使います（`admin-only.sql`）。一般公開の権限を追加するSQLや本番データの初期化は不要です。旧ドメインや別のブラウザーのlocalStorageは自動取得できないため、以前入力した場所で保存する必要があります。

「数字を入力」は、変更した項目だけを保存し、別の項目を空欄や古い値で上書きしません。未入力の絞り込み・日付切り替え・通信失敗・保存中の追加入力でも下書きを保持し、数字と登録者総数を読み直して一致した項目だけ下書きを解除します。選択した記録日も維持します。日付を変えたときの空欄は、その日の記録がないことを表し、以前の数値の削除ではありません。履歴はページ分割して取得します。

制作プロンプトは生成時に保存済みの数字を再取得し、現在入力している土台と、項目ごとの計測日を含めます。未保存の数字は集計に含みません。古い固定の実測メモは使わず、直近の投稿と最新記録から比較します。「平均再生率」は平均視聴秒数÷尺であり、完走した人の割合ではありません。投稿から48時間以降の計測がある回を区別します。本番の私的な記録をコードに埋め込まないでください。

回帰テスト：`NODE_USE_ENV_PROXY=1 CHROMIUM_PATH=/usr/bin/chromium node --test tests/shorts.cjs`。既存のPlaywrightを使い、Supabaseはすべて模擬します。本番データを読み書きしません。

### 冒頭の反応と視聴時間・Seedance導入前後の比較

ダッシュボードの最重要KPIは、**視聴を継続した割合 → 平均再生率 → 1,000再生あたりの登録者数**です。「スワイプして次へ」は `100 − 視聴を継続` の補数として自動表示し、別入力・別KPIにはしません。「視聴を選んだ%」に保存していた `sv_metrics.stayed_pct` の値をそのまま使います。平均再生率は平均視聴秒数÷動画尺×100で算出し、完走率ではなく100%を超えることもあります。高評価率は高評価数÷再生数×100で、高評価÷（高評価＋低評価）とは区別します。登録は登録者増加÷再生数×1,000です。

利用手順：

1. 「土台」の「映像化の比較基準」で、YouTube Studioの**導入前の過去28日間・ショート**の終了日と「視聴を継続」を記録します。導入開始日はそれより後に設定し、「保存する」を押してください。既存の土台に追加して同じ `sv_config` に保存します。
2. 動画を編集し、「映像の制作手法」を「Seedanceを使用」または「Seedance以外」に設定します。これは `sv_videos.note` の先頭の `【制作手法:Seedance】` または `【制作手法:その他】` で保存し、既存のメモ本文を維持します。日付や題名から使用ツールを推測しません。バージョン・実際の映像・制作費などはメモに残せます。
3. 「数字を入力」で、投稿24時間後と4日後を目安に、同じ集計範囲の視聴継続・平均視聴秒数・再生・高評価・登録増加をStudioから転記します。視聴継続の入力中にもスワイプ率が更新されます。欠測を0にせず、0は実測値として保存します。
4. ダッシュボードで前後の中央値・差・各指標の入力本数・計測待ちを比較し、「次に作る動画」で同じ結果をプロンプトへ反映します。毎回違う案を探索する既定の動作は維持します。

**集計の違い**：Studioから転記した28日間のチャンネル集計値は参考として別表示します。動画ごとの割合の中央値や単純平均をStudioのチャンネル集計値と同一視しません。主要KPIカードは日本時間で直近28日間に投稿した動画が対象です。導入前後の表は、設定した導入前終了日までの28日間の投稿（Seedance以外・手法未記録を含む）と、導入開始日から28日間の投稿のうちSeedance使用を明記した動画だけを対象にします。未来の投稿は含めません。

動画ごとの比較では、投稿72〜120時間後の、96時間に最も近い1行を使います。再生数のある同じ行から他指標も読み、別の日の値で欠測を補いません。母数の再生が0なら登録率・高評価率は未算出です。期間が終わっていない、または同条件の計測行がない動画がある場合は暫定表示します。平均視聴時間・平均再生率のShortsにおける母集団と、総再生数の母集団は必ずしも同じではありません。集計条件をそろえて比較してください。

A/Bの改善提案は、視聴継続と平均再生率の両方がある動画を前後各3本以上必要とします。視聴継続が基準より5ポイント以上低下なら冒頭の改善、視聴継続が基準以上なのに平均再生率が5ポイント以上低下なら展開・テンポ・尺の改善を仮説として提案します。特定の1秒・3秒の離脱や、最後まで視聴した人数を断定しません。離脱箇所はStudioの維持率グラフで確認します。5ポイント・3本は運用上の目安で、尺・テーマ・配信対象の違いもあるため、前後差だけでSeedanceの効果や投資価値は確定しません。

**自動取得は追加していません。** Studio表示とYouTube Analytics APIの取得可否・定義が同じとは限らないため、今回の入力は手動です。公開仕様の確認先：[YouTubeのコンテンツ分析](https://support.google.com/youtube/answer/12942217?hl=ja)、[Analytics APIの指標](https://developers.google.com/youtube/analytics/metrics)。SeedanceのAPI連携も追加していません。プロンプトは利用できる場合の冒頭0〜5秒の検証を指示しますが、特定バージョンの機能は前提にしません。

`stayed_pct` 列がある環境ではSQL実行は不要です。列がない場合だけ、警告に従い `youtube-hook.sql` をSupabase SQL Editorで実行してください。既存値・RLS・権限を維持して列を追加するSQLです。クラウドDBには自動適用していません。SQLの再実行・データ・RLS保持は `tests/youtube-hook-db.sql` を使い、使い捨てPostgreSQLで検証します。

### 毎回違う実写アプローチを探索する（2026-10-21〜）

「次に作る動画」は、既定で生成のたびに別のアプローチを選びます。「別のアプローチを作る」も新しい案へ進みます。以前のように動画を登録するまで同じ案を出し続けたり、成績の良い型へ自動で戻ったりしません。「今回の作り方」で「数字に手応えのある型を再検証する」を明示的に選んだ場合だけ、比較条件を満たす型を再検証します。候補がなければ探索します。

一人称の小さな冒険、手仕事の接写、屋外の短いドラマ、自然の観察、街のドキュメンタリー、視点が変わる発見、体を動かす解放感、小さな可笑しさの8系統から選びます。各系統に異なる3場面を用意し、次の周では場面を変えます。4周目以降は例の再使用を禁止し、履歴にない場所・被写体・出来事への作り替えを指示します。制作するAIには3案を検討させ、場面・被写体・動作・撮り方・物語・音のうち直近から4項目以上変えるよう求めます。これは生成指示であり、出力された動画の違いや品質をサイトが自動判定する機能ではありません。

実写に近い自然な動きを優先し、コード描画・図形・文字アニメ・静止画のズームだけでの代替は認めません。動画生成ツールまたは利用許諾のある実写動画素材と編集環境が必要です。利用できない場合は不足条件を伝えるよう指示します。サイト自体に動画生成APIは追加していません。音入りmp4を1本、題名、コピー用の説明文、計測リンク、記録用の1行という受け取り方は継続します。保存済みの「分析の土台」は保持し、古い映像指定と矛盾する場合は今回の探索・実写方針を優先する旨をプロンプトに明記します。

生成履歴は新しいlocalStorageキー `sv-prompt-exploration-v2` に保存します。直近24案と系統ごとの進行を持ち、再読み込み後も次へ進みます。履歴を保存できない場合は画面で知らせ、開いている間はメモリー上で別案へ進みます。別ブラウザー・別ドメインには生成履歴を自動転送しませんが、登録済みの形式名も確認して使用済みの案を避けます。履歴は投稿本数や成績に数えません。読み込み失敗時は案を消費しません。

完成した動画は、形式名（例：`探索1｜実写・一人称の小さな冒険`）をそのまま「形式」に入力し、メモに実際の場面・被写体・動作・撮り方・物語・音・仮説を残してください。次の制作では直近の投稿メモも参照します。別案を作るだけでは動画識別子は増えないので、完成した動画ごとに登録してから次の動画を制作してください。過去の動画、形式名、保存済みの土台・数字は変更しません。DBの変更や再初期化も不要です。

比較には直近90日の投稿済み記録だけを使います。投稿4日後を目安に数字を記録してください。日付しかないため、日本時間の日付の開始時刻で投稿72〜120時間後に当たる行を選び、96時間後に最も近い行の再生・視聴・登録を比較します。日付が異なる項目は混ぜず、欠測は0にしません。24時間後の記録も残せますが、この選定とは別です。

再検証候補は視聴を継続した割合を最優先にします。同じ形式名の直近3本のうち2本以上で、他形式（比較可能な直近最大30本、視聴継続の入力が最低3本）の視聴継続中央値を5ポイント以上上回り、候補自体の視聴継続中央値も5ポイント以上高い場合です。再生数1.3倍の条件は外し、平均再生率と登録を併記して再検証します。1回だけの探索結果は一覧で比較できますが、候補の判定には同じ形式名で追加の検証が必要です。小標本の運用上の目安で、統計的な有意差や成功の保証ではありません。

再検証モードでも同じ型を2本続けたら探索へ戻ります。直近の反応低下、記録不足、結果待ちで判定条件を満たさなくなれば探索します。生成直後の「今回の検証設計」は生成されたプロンプトと一致します。

## BBSの公開前チェック

**コードを配置しただけでは保護は有効になりません。下記のSQL・環境変数・Vercelデプロイが必要です。**

新規投稿・返信・管理者による編集を `/api/bulletin` に送り、名前と本文をAIで確認してから保存します。攻撃、嫌がらせ、差別、脅迫、宣伝などを拒否する方針です。本人のつらさの吐露や相談、穏やかな建設的意見は区別します。
拒否・判断保留の原文はサイトのDB・管理画面・アプリのログには保存せず、通知もしません。判定失敗・タイムアウト・設定不足のときは投稿を止め、未審査のまま公開する代替経路は設けません。AIにも見逃し・誤判定があり、完全な遮断は保証できません。既存の投稿は再判定しません。

通知メールは公開された新規投稿の存在とリンクだけを送り、名前・本文・返信先の引用を一切含めません。既存の通知トリガーを使い、未導入のメール通知は勝手に有効にしません。通知APIのエラーで投稿が二重送信されないよう、メール失敗で保存を取り消さない設計です。

### 判定・連投制限・データの扱い

- 判定モデルは `gpt-4.1-mini-2025-04-14`。基準は `api/bulletin.js` の `POLICY` にあります。文字列中の指示は審査対象として扱いますが、AIによる判定回避を完全には防げません。
- `allow` を明示的に返した場合だけ保存します。新規投稿だけでなく返信と編集も同じ判定を通します。編集者はSupabase Authで確認し、管理者のUIDと照合します。
- 同じIPから30秒に1回・UTC日付で1日20回、サイト全体で1日200回までの判定受付です。拒否やAPI障害も受付回数に含みます。共有回線では枠を共有し、全体上限では全員の投稿が一時停止します。値はSQL関数内で調整できます。
- IPはサーバーの秘密鍵を使う日替わりHMACにして回数制限にのみ使用します。DBにはそのハッシュと回数・時刻だけを残し、当日と前日より古い記録は次回受付時に削除します。
- 名前・本文と、返信の場合は返信先の内容をOpenAIへ送ります。フォームにも明示しています。`store: false` を指定しますが、これは提供元でのすべての保持をゼロにする保証ではありません。API側のデータ取扱設定は別途確認してください。
- サイト内に未承認投稿を読む審査待ち一覧は作りません。旧投稿やAIの見逃しを含め、目にする可能性をゼロにするには第三者による公開前確認などが別途必要です。

実装時に確認した公式資料: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini)、[Supabaseの権限とRLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Vercel Node.js Functions](https://vercel.com/docs/functions/runtimes/node-js)、[VercelのIPヘッダー](https://vercel.com/docs/headers/request-headers)。

### BBSのテスト

公開サイトで保存せずに接続を確認するには、`POST /api/bulletin` に `{"action":"check"}` をJSONで送ります。固定の挨拶だけをAIに送り、投稿・通知は作りません。通常投稿と同じ30秒・日次の制限を使い、API料金の対象になります。成功時は `{"ok":true,"decision":"allow"}`、失敗時は `diagnostic` に原因の種類だけを返します。任意の名前・本文を渡しても診断には使いません。これは接続と固定文の判定の確認で、保存・管理者UID・あらゆる内容の分類精度の検証ではありません。

`ai_insufficient_quota` / `ai_quota` はAPI利用枠、`ai_credit_balance_exhausted` は前払い残高、`ai_project_spend_limit_exceeded` / `ai_organization_spend_limit_exceeded` は支出制限を確認してください。`ai_auth` はAPIキー、`ai_access` はアクセス権、`ai_model` はモデル、`ai_request` はリクエスト仕様、`ai_response_failed` は応答形式を確認します。通常の投稿画面には内部の診断情報や提供元の生のエラーメッセージを表示しません。[OpenAI公式のエラー一覧](https://developers.openai.com/api/docs/guides/error-codes)

`node --test tests/bbs-api.cjs` で許可・拒否・判定保留・障害・不正入力・返信・管理者認証・回数制限を確認します。AI/DBの応答は模擬するため、実際のAIの分類精度や本番設定は検証しません。
`node tests/retro.cjs` には、投稿と返信の拒否時の入力保持、判定障害時の停止、許可時のみ一覧に出ること、Supabaseへの直接書き込みがないことも含みます。

PostgreSQL 16でSQLの権限・トリガー・通知・回数制限・再実行を確認できます。これは外部ネットワークを使わない使い捨てDBで、本番には接続しません。

```sh
docker run --rm --network none --tmpfs /var/lib/postgresql/data \
  --mount "type=bind,source=$PWD,target=/work,readonly" \
  -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16 sh /work/tests/run-bbs-db.sh
```

ローカルのHTMLバックアップや確認できた作業記録には、変更直前の実際の人数を確定できる記録が見つからなかったため、人数は変更していません。テスト内の999/1000は模擬値で、本番の人数ではありません。
ドメインが変わるとブラウザの1日1回の記録が引き継がれず、同じブラウザでも新ドメイン初回に1回加算される可能性はありますが、DBの累計値そのものはドメイン単位で分かれていません。アクセス履歴全体を保存する仕組みはなく、`sv_site_visits` はUTM付き流入のみの別集計なので復元用の累計として使えません。

## 動作確認

PlaywrightとChromiumがある環境で次を実行します。

```sh
node tests/retro.cjs
```

必要に応じて `PLAYWRIGHT_PATH` でPlaywrightのモジュール位置、`CHROMIUM_PATH` でChromiumの実行ファイルを指定できます。
テストはローカルHTTPサーバーを起動します。最初の実行ではサイトが使うSupabaseの公開CDNファイルを一時フォルダに取得します。
Supabaseへの通信はすべてテスト内で置き換えるため、本番の投稿・プロフィール・訪問者数は変更しません。

確認範囲は、ログイン、プロフィールの編集・保存・失敗・再表示・匿名閲覧、ログアウト、日記との分離、日記の編集（詳細画面・一覧から、保存失敗時の入力保持、未保存のまま閉じるときの確認、訪問者には編集ボタンが出ないこと）、100件を超える日記の追加取得、閲覧数の列がないときの非表示、HTMLの文字列表示、カウンターの重複防止と通信失敗時の再試行、ナビゲーションと既存モーダルです。
レスポンシブ表示はタッチ端末のエミュレーションで320〜1440pxの9段階を通常文字・大きい文字の両方で確認し、横へのはみ出し、本文サイズ、主要なタップ領域を検査します。プロフィール編集では小型画面、横向き、高さ460pxの画面でも保存ボタンに到達できることを確認します。実機のソフトウェアキーボード操作は対象外です。
スクリーンショットはOSの一時フォルダ内の `my-site-check` に保存します（`TEST_OUTPUT` で変更可能）。実際の管理者アカウントでの本番保存は自動テストの対象外です。
